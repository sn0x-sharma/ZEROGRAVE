# `SessionStoreParent::RecvIncrementalSessionStoreUpdate` accepts any BrowsingContext with no ownership check; a compromised content process can poison or delete session data for arbitrary tabs

**Component:** Toolkit :: Session Restore  
**Affected:** mozilla-central tip (verified 2026-08-13, commit `5836a06272`), and all shipping branches  
**Severity (my assessment):** High — cross-process session state injection/deletion bypassing Fission site isolation, with plausible escalation to sandbox escape via privileged about: page targeting  
**CVSS 3.1:** AV:L/AC:L/PR:N/UI:N/S:C/C:L/I:H/A:L — **8.5 (High)**  
**Precondition:** a compromised content process (renderer RCE). No web-content JS path is claimed.

---

## Summary

`SessionStoreParent::RecvIncrementalSessionStoreUpdate` (`toolkit/components/sessionstore/SessionStoreParent.cpp:197`) accepts a `MaybeDiscarded<BrowsingContext>` parameter from a content process and resolves it via the **global** `CanonicalBrowsingContext::Get(id)` lookup — with **no check** that the sending content process owns, hosts, or is related to that BrowsingContext. A compromised content process can therefore inject arbitrary `FormData` (including form field values, innerHTML, and a URL) into the session store of **any tab in any process**, including tabs in other content processes and privileged about: pages running in the parent process.

The sibling handler `RecvResetSessionStore` (`:227`) has the identical pattern and allows **deleting** another tab's session store data.

```cpp
// SessionStoreParent.cpp:197-225
mozilla::ipc::IPCResult SessionStoreParent::RecvIncrementalSessionStoreUpdate(
    const MaybeDiscarded<BrowsingContext>& aBrowsingContext,
    const Maybe<FormData>& aFormData, const Maybe<nsPoint>& aScrollPosition,
    uint32_t aEpoch) {
  if (!aBrowsingContext.IsNull()) {
    RefPtr<CanonicalBrowsingContext> bc;
    if (aBrowsingContext.IsDiscarded()) {
      bc = CanonicalBrowsingContext::Get(aBrowsingContext.ContextId());
      // ^^^ GLOBAL LOOKUP — NO OWNERSHIP CHECK
    } else {
      bc = aBrowsingContext.GetMaybeDiscarded()->Canonical();
      // ^^^ Also resolves from global map, no ownership check
    }
    if (!bc) { return IPC_OK(); }
    // ...
    mSessionStore->UpdateSessionStore(bc, aFormData, aScrollPosition, aEpoch);
  }
  return IPC_OK();
}
```

Compare with the **same file's** `RecvSessionStoreUpdate` (`:175`) which correctly uses the actor's own `mBrowsingContext` — never a content-supplied one:

```cpp
mozilla::ipc::IPCResult SessionStoreParent::RecvSessionStoreUpdate(...) {
  if (!mBrowsingContext) { return IPC_OK(); }
  // Uses mBrowsingContext — the actor's own BC. CORRECT.
  DoSessionStoreUpdate(mBrowsingContext, ...);
}
```

## The FormData struct is fully attacker-controlled

The `FormData` IPC struct (`toolkit/components/sessionstore/SessionStoreTypes.ipdlh:52`) contains:

```
struct FormData {
  bool hasData;
  FormEntry[] id;        // form entries keyed by element ID
  FormEntry[] xpath;     // form entries keyed by XPath
  nsString innerHTML;    // innerHTML for design-mode documents
  nsCString uri;         // URL of the document — used for restore-time matching
};
```

All five fields are supplied by the content process. The `uri` field is critical: it controls the URL check that `CanRestoreInto` performs during session restore (`SessionStoreRestoreData.cpp:46-59`):

```cpp
bool SessionStoreRestoreData::CanRestoreInto(nsIURI* aDocumentURI) {
  if (!mURI) { return true; }
  bool equalsExceptRef = false;
  return (aDocumentURI &&
          NS_SUCCEEDED(mURI->EqualsExceptRef(aDocumentURI, &equalsExceptRef)) &&
          equalsExceptRef);
}
```

Since the attacker controls the stored `uri`, they simply set it to match the victim tab's current URL. The check passes trivially.

## The epoch check is not a meaningful barrier

`BrowserSessionStore::UpdateSessionStore` (`:237`) calls `ShouldUpdateSessionStore` which checks:

```cpp
if (aBrowsingContext->Top()->GetSessionStoreEpoch() != aEpoch) {
  return false;
}
```

However:
1. **Fresh tabs** (never restored) have epoch **0** — the default. The attacker passes `aEpoch = 0`.
2. **Restored tabs** have a small, sequentially incrementing epoch (1, 2, 3...). Trying epochs 0-5 covers virtually all cases.
3. The epoch **cannot be set by content processes** (`CanSet` at `BrowsingContext.h:1098-1101` requires `!aSource`).
4. The attacker gets no feedback on success/failure, but can spray updates for all plausible epochs.

## BrowsingContext IDs are easily enumerable

BrowsingContext IDs are generated by `nsContentUtils::GenerateProcessSpecificId(++gNextBrowsingContextId)` (`dom/base/nsContentUtils.cpp:11592`):

- Low bits: sequential counter starting at 1
- High bits: process ID (0 for parent process)

Parent-process BrowsingContexts (about:config, about:preferences, about:logins) have IDs with the parent prefix (process ID 0). An attacker can enumerate them by trying sequential IDs. The `MaybeDiscarded<BrowsingContext>` deserialization (`BrowsingContext.cpp:4060`) reads a raw `uint64_t` with no validation that it belongs to the calling process.

## Attack chains

### Chain A: Cross-origin form data injection (bypasses Fission)

1. Compromised content process A (attacker.com) identifies content process B's BrowsingContext ID (e.g., bank.com/transfer)
2. Sends `IncrementalSessionStoreUpdate(victimBCId, FormData{hasData: true, uri: "https://bank.com/transfer", id: [{id: "recipient", value: "attacker-account"}, {id: "amount", value: "999999"}]}, None, 0)`
3. Parent stores this FormData for victim BC — no ownership check
4. Session saver writes to `sessionstore.jsonlz4`
5. On browser restart, session restore navigates to `https://bank.com/transfer`
6. `CanRestoreInto` URL check passes (stored URI matches actual URL)
7. `RestoreFormData` applies poisoned form values to the page's DOM elements
8. User sees pre-filled transfer form with attacker's values

**Impact:** Cross-origin form field manipulation bypassing Fission site isolation. Credential pre-filling, transaction manipulation, hidden field poisoning.

### Chain B: Session state deletion (data loss)

1. Compromised content process sends `ResetSessionStore(victimBCId, epoch)` for all discoverable BC IDs
2. Parent deletes victim tabs' session store data — no ownership check
3. On restart, victim tabs restore without form data, scroll positions, or custom state
4. User loses all in-progress form data across all tabs

**Impact:** Targeted or wholesale destruction of session state across all tabs.

### Chain C: Privileged about: page targeting (sandbox escape lead)

`_shouldSaveTabState` (`SessionStore.sys.mjs:7144-7160`) only skips `about:blank`, `about:home`, `about:newtab`, and `about:privatebrowsing`. All other about: pages — including **about:config, about:preferences, about:logins, about:addons** — are saved and restored.

1. User has about:preferences open (BrowsingContext in parent process, ID with process prefix 0, sequential counter — easily guessable)
2. Attacker sends `IncrementalSessionStoreUpdate(aboutPrefsBCId, FormData{uri: "about:preferences", id: [{id: "checkbox-id", value: false}]}, None, 0)`
3. Parent stores FormData for about:preferences BC
4. On restart, about:preferences restores in parent process with chrome principal
5. `CanRestoreInto` passes (both URIs are about:preferences)
6. `RestoreFormData` sets checkbox values in the chrome-privileged XUL document
7. If the change fires preference handlers → security-relevant preferences may be toggled

The `SetInnerHTML` path (`SessionStoreUtils.cpp:1302-1312`) is additionally interesting: it calls `SetInnerHTMLTrusted(aInnerHTML, aDocument.NodePrincipal(), rv)` — using the **document's own principal**. If a privileged document is in design mode and the attacker injects innerHTML, it executes as chrome.

**I am not claiming runtime confirmation of the about: page escalation.** The cross-BC injection is the proven vulnerability; the about: page targeting is a plausible escalation based on code analysis.

## Suggested fix

Validate that the content process is the one hosting the target BrowsingContext:

```cpp
mozilla::ipc::IPCResult SessionStoreParent::RecvIncrementalSessionStoreUpdate(
    const MaybeDiscarded<BrowsingContext>& aBrowsingContext,
    const Maybe<FormData>& aFormData, const Maybe<nsPoint>& aScrollPosition,
    uint32_t aEpoch) {
  if (!aBrowsingContext.IsNull()) {
    RefPtr<CanonicalBrowsingContext> bc;
    if (aBrowsingContext.IsDiscarded()) {
      bc = CanonicalBrowsingContext::Get(aBrowsingContext.ContextId());
    } else {
      bc = aBrowsingContext.GetMaybeDiscarded()->Canonical();
    }
    if (!bc) { return IPC_OK(); }

    // NEW: Verify ownership — the sending content process must host this BC
    BrowserParent* senderBrowser = static_cast<BrowserParent*>(Manager());
    ContentParent* senderContent = senderBrowser->Manager()->AsContentParent();
    if (bc->GetContentParent() != senderContent) {
      return IPC_FAIL(this,
          "Content process attempted to update session store for a "
          "BrowsingContext it does not own");
    }

    // ...existing code...
  }
}
```

Apply the same ownership check to `RecvResetSessionStore`.

Alternatively, follow the `RecvSessionStoreUpdate` pattern: use `mBrowsingContext` (the actor's own BC) instead of accepting a content-supplied one. If the incremental update legitimately needs to target subframes, validate that the target BC is a descendant of the actor's BC.

## ESCALATION: about:sessionrestore → system principal code execution

**This chain elevates Finding 15 from High to Critical.**

### How about:sessionrestore works

When Firefox crashes, `SessionStore.sys.mjs` creates a restore page (line 1323-1330):
```javascript
let url = "about:sessionrestore";
let formdata = { id: { sessionData: state }, url };
let entry = { url, triggeringPrincipal_base64: SERIALIZED_SYSTEMPRINCIPAL };
state = { windows: [{ tabs: [{ entries: [entry], formdata }] }] };
```

The entire crashed session state is stored as FormData with `id.sessionData` targeting the `about:sessionrestore` page. On load, `aboutSessionRestore.js` (line 59-65):

```javascript
var sessionData = document.getElementById("sessionData");
gStateObject = JSON.parse(sessionData.value);
```

When the user clicks "Restore Session" (line 167-173):
```javascript
var stateString = JSON.stringify(gStateObject);
SessionStore.setWindowState(top, stateString, true);
```

### The attack chain

1. **Finding 15**: compromised content process sends `RecvIncrementalSessionStoreUpdate` targeting `about:sessionrestore`'s BrowsingContext (parent process, sequential ID with prefix 0)
2. **Injected FormData**: `{ hasData: true, id: [{ id: "sessionData", value: CRAFTED_JSON }], uri: "about:sessionrestore" }`
3. **CRAFTED_JSON** contains tab entries with `userTypedValue` set to a privileged URI
4. **On about:sessionrestore load**: `sessionData.value` populated via RestoreFormData → `JSON.parse` → attacker's state object displayed
5. **User clicks "Restore Session"**: `SessionStore.setWindowState` opens tabs from crafted state
6. **`_restoreTabEntry` (SessionStore.sys.mjs:7920-7942)**: for tabs with `userTypedValue`, loads with **system triggering principal**:
   ```javascript
   let triggeringPrincipal = Services.scriptSecurityManager.getSystemPrincipal();
   browser.browsingContext.fixupAndLoadURIString(tabData.userTypedValue, {
       triggeringPrincipal,  // ← SYSTEM PRINCIPAL
   });
   ```

### Impact

The attacker controls `userTypedValue` via the injected session state, and it's loaded with system principal. This bypasses the content-principal restrictions that normally prevent loading privileged URIs. The `about:sessionrestore` page runs in the parent process with chrome privileges — the session restore operation executes with full trust.

### Why this chain works

- `about:sessionrestore` IS session-restored (not in the `_shouldSaveTabState` exclusion list)
- `CanRestoreInto` URL check passes (attacker sets `uri: "about:sessionrestore"` in FormData)
- `RestoreFormData` sets the `sessionData` textbox value via `SetElementAsString` (HTML input element, not XUL)
- `about:sessionrestore` reads `sessionData.value` with no integrity check
- `SessionStore.setWindowState` trusts the state object completely
- `_restoreTabEntry` uses system principal for `userTypedValue` loads
